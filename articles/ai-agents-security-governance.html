وكلاء الذكاء الاصطناعي: الصلاحيات والبيانات والإشراف البشري قبل التشغيلAI Agents: Permissions, Data Boundaries, and Human Oversight Before Deployment

نُشر في 23 نوفمبر 2026 · قراءة 12 دقائقPublished November 23, 2026 · 12 min read

تحليل عملي لمخاطر الوكلاء القادرين على استخدام الأدوات وتنفيذ إجراءات متعددة الخطوات وكيفية ضبطهم.A practical analysis of tool-using AI agents, multi-step actions, and safeguards for responsible deployment.

النسخة العربية

ما الذي يميز الوكيل عن المساعد النصي؟

قد يكتفي المساعد النصي باقتراح إجابة، بينما يستطيع الوكيل استخدام أدوات أو واجهات أو ملفات لتنفيذ خطوات متتابعة. هذه القدرة تنقل المخاطر من جودة النص إلى صلاحيات الفعل: فقد يرسل رسالة أو يعدّل سجلاً أو ينشئ مورداً أو يكشف بيانات إذا كانت صلاحياته واسعة أو توجيهاته غير محكمة.

ابدأ بأقل صلاحية ممكنة

امنح الوكيل الأدوات اللازمة للمهمة فقط، وافصل القراءة عن الكتابة، وحدد النطاقات والمجلدات والحسابات المسموح بها. لا تضع مفاتيح سرية داخل المطالبات أو الملفات التي يمكن للوكيل قراءتها. استخدم بيانات اعتماد قصيرة العمر، وسجّل كل إجراء يمكن أن يغير حالة نظام خارجي.

احمِ الوكيل من حقن التعليمات

قد تحتوي صفحات الويب والرسائل والمستندات على نصوص خبيثة تحاول تغيير سلوك الوكيل. تعامل مع المحتوى المسترجع كبيانات غير موثوقة، لا كتعليمات أعلى أولوية. افصل تعليمات النظام عن محتوى المستخدم والمصادر، وقيّد الأدوات التي يمكن استدعاؤها بعد قراءة محتوى خارجي.

اجعل الأفعال الحساسة تتطلب موافقة

الإرسال والحذف والتحويل المالي وتغيير الصلاحيات والنشر العام يجب أن تخضع لتأكيد بشري واضح. اعرض للمراجع ملخصاً لما سيحدث، والوجهة، والبيانات المتأثرة، وإمكانية التراجع. استخدم بيئة اختبار قبل الإنتاج، وحدوداً للإنفاق ومعدلات التنفيذ، وآلية إيقاف طارئ.

راقب النتائج لا النوايا فقط

احتفظ بسجلات للأدوات والمدخلات والمخرجات والقرارات، مع حماية البيانات الحساسة في السجلات. اختبر حالات الفشل والتكرار وتعارض التعليمات وتسرب البيانات. قيّم الوكيل دورياً بعد تغيير النموذج أو الأدوات أو الصلاحيات؛ فالاختبار الناجح في بيئة صغيرة لا يثبت سلامة التشغيل في كل الظروف.

English edition

How an agent differs from a chat assistant

A text assistant may only suggest an answer, while an agent can use tools, interfaces, or files to perform a sequence of actions. This shifts risk from text quality to action authority: an agent might send a message, edit a record, create a resource, or expose data if permissions are broad or instructions are poorly constrained.

Begin with least privilege

Give the agent only the tools required for its task. Separate read access from write access, and scope allowed accounts, folders, and resources. Do not place secrets in prompts or files the agent can inspect. Use short-lived credentials and log every action that can change an external system.

Defend against prompt injection

Web pages, messages, and documents may contain malicious text designed to redirect an agent. Treat retrieved content as untrusted data, not as higher-priority instructions. Keep system instructions separate from user and source content, and restrict which tools may be called after external content is read.

Require approval for sensitive actions

Sending, deleting, transferring funds, changing permissions, and public publishing should require explicit human confirmation. Show the reviewer what will happen, the destination, affected data, and whether the action can be reversed. Use a test environment before production, spending and rate limits, and an emergency stop.

Monitor outcomes, not intentions

Keep logs of tools, inputs, outputs, and decisions while protecting sensitive information in those logs. Test failures, retries, conflicting instructions, and data leakage. Reassess the agent after changing its model, tools, or permissions; success in a small test does not prove safety in every operating condition.
